# Product Prover review — parcel locker deposit

**Product Prover version:** 4.3.0
**Mode:** FULL
**Reviewed document:** `parcel-locker-spec.md`
**Scope:** controlled demonstration for the article, not a review of a shipped product or a production specification.

## Triage

**TRIAGE: PROCEED** — this is a short but analyzable product specification. It names actors, lifecycle events, a collection promise, and an automated expiry rule.

## Opening assessment

This design describes a simple parcel hand-off: a courier deposits a parcel, the recipient receives a code, and the locker should release the parcel during a 72-hour collection window. The basic journey is easy to follow, and naming the nightly sweep is good because it makes the time-based lifecycle visible. The document also separates deposit, collection, and expiry rather than mixing them into one vague story. But its main state is declared before the recipient can use it, and both collection and expiry stop without a defined outcome. The stated 72-hour promise also cannot be kept by a job that runs only nightly. This needs significant rework before implementation, because different developers can make mutually incompatible but individually plausible choices.

## The model

### Entities and relationships

- **Parcel** — occupies one locker compartment and carries the lifecycle state.
- **Locker compartment** — is selected by the courier, opened for deposit or collection, and is controlled by the locker controller.
- **Pickup code** — is generated for a stored parcel and sent through the notification service; its storage, expiration, and invalidation are not specified.
- **Notification service** — sends the SMS but has no stated acknowledgment, failure, or retry behavior.

### States of a parcel

1. **Unassigned** *(inferred)* — before a courier selects a compartment; exits when deposit begins.
2. **Stored** — entered after the controller records the parcel; the document intends collection or expiry to follow.
3. **Expired** — entered by the nightly sweep after the collection window; no exit is stated.
4. **Collected** *(missing from the document)* — should be entered after a recipient takes the parcel; no such state is specified.

### Actor-action assignments

- “Deposit parcel” — courier, through the handheld scanner and locker controller.
- “Generate and send pickup code” — system / notification service.
- “Collect parcel” — recipient, through the locker.
- “Mark expired” — nightly sweep (automated).
- “Remove or return an expired parcel” — initiator not stated.

### What I assumed

- I read `Stored` as a state a recipient may collect from, because the collection section calls a code valid without naming another availability state.
- I read “has 72 hours” as an exact customer-facing promise from the moment the parcel becomes available for collection, not “until the next nightly job.”
- I found no authoritative surface for pickup-code generation or message delivery named in this doc. If one exists in the product, this deposit flow does not state how it records success or failure.
- Security requirements, carrier integrations, pricing, and identity verification are out of scope only because this demo spec says nothing about them; their absence must not be mistaken for a policy decision.

## Structural issues in the model

F1 — `Stored` is entered before the collection path is made usable

> “The locker controller marks the parcel `Stored`. The system generates a pickup code and sends the code to the recipient by SMS.” — Deposit, steps 3–4

If code generation or SMS queuing fails after `Stored` is recorded, the recipient has a parcel that appears stored but no usable way to collect it. Support sees a missing-code complaint while the locker remains occupied, and a retry can create an ambiguous second code or message.

Add either a `DepositPending` / `CodePending` state with a recovery path, or make the transition to `Stored` occur only after a pickup code is durably recorded and delivery has been queued. I prefer the explicit intermediate state: it makes a failed hand-off observable and recoverable.

`defect · partial-success-risk (atomicity)`

F2 — Collection has no terminal state or code-reuse rule

> “If the code is valid, the locker opens the compartment and the recipient takes the parcel.” — Collection

After the recipient takes the parcel, the document never says who records that the compartment is empty, whether the code becomes invalid, or what happens if the same code is entered again. A recipient or an operator can encounter a reopened empty compartment, a still-valid code, or a compartment that cannot be reused with no agreed way to resolve it.

Add a `Collected` state entered only after door-close confirmation and empty-compartment confirmation; invalidate the code at that transition and return the compartment to the available inventory. State the recovery behavior when the door opens but the confirmation is missing.

`defect · missing-outcome-check (postcondition)`

## Property analysis

F3 — An expired parcel has no defined operational exit

> “The nightly sweep marks a stored parcel `Expired` when its collection window has elapsed.” — Expiry

An operator can see an expired parcel occupying a compartment but has no instructed action, owner, or endpoint for it. The compartment can remain unavailable indefinitely, while the recipient has no stated outcome and support has no policy to communicate.

Add an `Expired → ReturnPending → Returned` or `Expired → ReadyForOperatorRemoval` flow. Name the actor who starts it, the deadline for removal, the recipient notification policy, and the condition that returns the compartment to service.

`defect · no-exit (dead-end)`

F4 — A nightly sweep cannot enforce a 72-hour collection promise

> “The recipient has 72 hours to collect a stored parcel.” — Deposit
> “The nightly sweep marks a stored parcel `Expired` when its collection window has elapsed.” — Expiry

A parcel that reaches 72 hours just after the nightly sweep can remain collectible for almost another day. The recipient sees a code work after the stated deadline, or an operator treats two different elapsed times as equivalent, so the system breaks its own customer-facing promise.

Choose one rule and write it into the spec: either enforce expiry at `stored_at + 72 hours` at code validation and use the nightly sweep only for cleanup, or change the promise to a named nightly-cutoff policy. I recommend exact validation at collection, because the document already promises “72 hours.”

`defect · unenforceable-promise (discharge)`

F5 — The spec has no cross-cutting rule for failure visibility or recovery

> “The system generates a pickup code and sends the code to the recipient by SMS.” — Deposit, step 4

The notification service can be delayed, rejected, or unavailable, but no user or operator outcome is stated. A recipient waits without knowing whether to retry, while support lacks a parcel identifier, failure status, or repair action and the system may silently leave capacity blocked.

Add a “Failure and recovery” section covering code-generation failure, SMS-queue failure, locker-door confirmation failure, and sweep failure. For each case, name the visible status, retry owner, operator action, and event log fields; add a test row for each surface it governs.

`defect · hard-to-monitor (observability)`

## Human and operational factors

F6 — A recipient has no visible outcome when the code path fails

> “The system generates a pickup code and sends the code to the recipient by SMS.” — Deposit, step 4

When the SMS is delayed or a code is rejected at the locker, the recipient has no stated message, alternate path, or support identifier. The recipient is left at the locker with a parcel they cannot collect, while an operator cannot distinguish an invalid attempt from a notification or locker failure.

Specify the recipient-facing messages for “code not yet available,” “code expired,” and “code rejected,” plus a support reference tied to the parcel and locker. State whether the recipient may request a new code and under what limit.

`defect · confusing-for-users (cognitive-load)`

## Closing summary

### Top fixes before development

1. **F1:** Do not expose `Stored` before a durable, recoverable collection path exists.
2. **F4:** Make the 72-hour rule enforceable at code validation, not dependent on a nightly sweep.
3. **F2 and F3:** Complete the lifecycle with `Collected` and an operator-owned expiry/return path.

### Paste-ready properties for the specification

- A parcel enters `Stored` only after its pickup code is durably recorded and a notification has been queued; otherwise it remains in a recoverable `CodePending` state visible to operators.
- At `stored_at + 72 hours`, the pickup code cannot open the compartment. The nightly sweep may clean up overdue parcels but does not extend collection eligibility.
- A parcel enters `Collected` only after the door closes and the locker confirms the compartment is empty; that transition invalidates the pickup code and releases the compartment.
- Every `Expired` parcel has a named operator-owned transition to return or removal, with a deadline and a recipient-notification policy.

### Decisions still needed from the author

- Does “72 hours” mean an exact timestamp or a nightly cutoff? The current wording supports the exact timestamp; the review recommends enforcing it at code validation.
- Is notification delivery itself required before collection is possible, or is durable code generation plus a retryable message queue sufficient? The review recommends the latter, with a visible `CodePending` state.
